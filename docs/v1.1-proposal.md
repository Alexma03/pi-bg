# pi-bg v1.1 proposal (under judgment)

Context: the v1 in this tree was built and lab-tested (see `docs/manual-test-plan.md`; results in the research report). v1.1 is agreed with the user and not yet built.

## Operating model (user decision)

There are three orthogonal delegation layers:

| Layer | Purpose | Lifetime |
| --- | --- | --- |
| **gentle subagents** (`subagent_run`) | In-session exploration and parallel work | Children of a Pi session |
| **Orca workers** (`orca orchestration worker-start`) | Other terminals, worktrees or repos | Supervised by a Run mailbox |
| **pi-bg `bg_run`** | Plain shell commands (gates, CI watches, deploys, log tails) | Killed on session exit or reload |

A coordinator and its Orca workers both keep using gentle subagents. pi-bg must never interfere with them. For example, the bridge is disabled in gentle subagent children (`GENTLE_PI_AGENTS_CHILD=1`), because they inherit `ORCA_TERMINAL_HANDLE`.

## Problem to solve

A coordinator stops, believing the work is done, while Orca workers are stalled. The failure is twofold:

1. the child ends its turn without `worker_done`;
2. the parent never re-checks.

The user wants the parent to always know the state of every worker it created, model-free where possible, "like gentle background subagents".

## Facts (Orca 1.4.212)

`orca orchestration worker-list --run <id> --json` is read-only and takes about 0.14 s. Each row has a `projection` with:

- `stage` = {worker, dispatch, detail, activity}. `activity` is one of `working | done | idle | blocked | unknown`. It comes from Orca's Pi agent-status hook; `blocked` means an interactive UI prompt is active.
- `outcome` = `in_progress | succeeded | failed | outcome_unknown | finished_unverified`.
- `liveness` = {verdict `live | unverifiable | exited`, reason such as `stale_status` after 30 min without a status post, observedAt}.
- `attention` = {categories `guidance | input | approval | failure | interruption | unverifiable | stale | root_completion`, requiresAction}.
- `nextAction` = {kind `none | release | recover | inspect`, argv}.

Rows come newest first and are paged at 100. Pi workers have no dispatch environment variable; only `ORCA_TERMINAL_HANDLE`.

## v1.1 features

### F1. Fleet watch (coordinator)

- **Polling.** While the bridge has a bound Run, poll `worker-list --run <run> --json` every 30 s. This is read-only.
- **Snapshots.** Keep a per-dispatch snapshot and emit one coalesced `pi-bg-fleet` custom message (steer + triggerTurn) only on transitions:
  - **stalled**: outcome `in_progress` and activity `done`/`idle` for at least 3 min (user-approved threshold);
  - **blocked**: activity `blocked` for at least 1 min;
  - **exited**: liveness `exited` while in progress (nextAction recover);
  - **attention**: `requiresAction` newly true (input, approval, failure, interruption);
  - **closure debt**: settled but not released (nextAction `release`);
  - **fleet idle**: no worker `working`, and at least one not settled or not released.
- **Decisions stay with the model** (user decision). The bridge never nudges a worker automatically.
- **Fast pickup.** After a bash `worker-start`, poll immediately so the new dispatch enters the roster.
- **Tools.**
  - `orca_workers`: a compact read-only table (name/title, dispatch, stage, activity with age, outcome, liveness, attention, nextAction).
  - `orca_watch {dispatchId, on: settled|stalled|blocked|any, note?}`: the note comes back verbatim inside the notice, so the plan survives ("when A0 finishes, start A1 review"). All Run workers are watched by default; `orca_watch` only adds notes and extra events.

### F2. Worker self-reminder (worker side)

- **Detection.** When the session is a dispatched Orca worker, detect it with a read-only `check --terminal $ORCA_TERMINAL_HANDLE --peek --json` from the worker itself, which returns `dispatchId`. Alternatively, parse the injected preamble (Task/Dispatch IDs).
- **Tracking.** Watch for the worker's own `orca orchestration send --type worker_done` (bash tool_call).
- **Reminder.** At `agent_settled` without `worker_done`, inject a one-time steer reminder: "you are the worker for dispatch X; send worker_done (succeeded|failed) or ask".
- **Safety.** Never in gentle subagent children, and never after `worker_done`.
- **Optional (v1.2).** A worker-mode mailbox bridge on `dispatch:<id>`.

### F3. UI (Gentle Shell compatible)

- **Card widget** "Background · Orca" via `setWidget`, in the style of the gentle Agents card. It is shown only when non-empty:
  - running tasks (label, elapsed, last line);
  - the Orca bridge row (run, phase, pending delivery age);
  - fleet rows (worker, activity with age, attention).
  - It is collapsible, and finished rows expire.
- **Why a widget.** Gentle's fullscreen sidebar renders only the fixed sections footer/agents/todo. `setStatus` shows only in the sidebar "Integrations" card or the narrow bottom bar.
- **Richer delivery cards.** A glyph and colour per type: `worker_done` ✔/✖ by payload outcome, `question` ?, `escalation` ⚠, `status` ·. Collapsed shows one line per message; expanded shows bodies. Task notices are green or red by exit.
- **Compact tool renderers** (`renderCall`/`renderResult`) for bg_* and orca_*.
- **Overlays** (`ctx.ui.custom`): `/bg` (tasks, live tail, cancel) and `/orca` (fleet, pending delivery, reply to a question).

### F4. Agent state block

- Each turn (`before_agent_start`), and only when non-empty, add a compact block to the system prompt:
  - running bg tasks;
  - bridge phase and pending delivery id;
  - fleet summary (for example "2 working, 1 stalled 5m without worker_done, 1 to release").
- Purpose: it keeps orca_ack and fleet state visible after compaction.

### F5. Guidance

- A short "which layer when" guide in the tool prompt guidelines and in the parent `AGENTS.md` (subagent vs Orca worker vs bg_run).
- The `AGENTS.md` Orca guide will say: with pi-bg, never start `check --wait` or orca-wait; use orca_ack / orca_inbox / orca_workers.

### F6. Research (not built yet)

Could an **Orca-side extension** show the parent/child hierarchy and dependencies of sessions (coordinator → workers → subagents) in Orca's session list, or offer more native interaction than the CLI? This covers Orca extension points such as agent hooks, skills, automations, artifacts, worktree comments and cardStatus.

## Open risks we already know

- **Read-only fleet polling** on the live coordinator Run, every 30 s.
- **Notice storms** when many workers change state at once (coalescing needed).
- **The pointer window**: between an actionable delivery and orca_ack there is no waiter, but the outstanding delivery suppresses the pointer (verified live).
- **Footer invisibility** in Gentle fullscreen at medium widths.
